# Shared brief — F11 … F18 (v0.2.0 work)

**Read this before writing or executing any of `plans/F1[1-8]-*.md`.** It is the
one place the eight plans agree. Each plan was written by an agent that could not
see the other seven — exactly the failure mode `CLAUDE.md` warns about for
F1–F10 — so where a plan contradicts this file, **this file wins**, and where
this file contradicts `ROADMAP_v0.1.0.md` § Reconciliation Decisions, the roadmap
still wins.

## Where these features came from

A single user request, split into eight. The verbatim asks:

1. Opening a word from today's card and pressing back lands on **Collection**,
   not on today's card. Back should return to wherever the user came from.
2. Badges and achievements should be **clickable**, opening a large modal with a
   picture of the medal and an explanation of what it means (e.g. "you created a
   daily card on Mother's Day"). This needs a **`/generate-badge-art` skill**,
   because badges will keep being added. The art style must conform to the
   existing UI — explicitly *not* the dark, bloody style of the tarot deck's
   skill that inspired it.
3. **Duplicate handling for vocab**, including the edge case where the user types
   a typo whose *correction* already exists in their collection.
4. **Semantic duplicate detection for journal entries** against the existing
   collection.
5. **Share pages** for a word, a daily card, and a journal entry — with a
   "practise this word" path that signs a stranger in, adds the word, and drops
   them into its chat.
6. A new badge: **"Sauron's Favorite"** — draw a daily card on the day J.R.R.
   Tolkien died (2 September).

## Locked decisions

These were made by the user in the planning conversation. Do not relitigate them
inside a plan; if one turns out to be wrong, stop and report it.

- **[S1] Badge art is raster, generated by OpenAI's image API.** The key is
  `OPENAI_API_KEY` and it lives in `.env.local`, which is gitignored. It is a
  *different key from `LLM_API_KEY`* and no application code may read it — only
  the skill's generation tool, which runs offline on a developer's machine. **The
  literal key appears in no file in this repository, including these plans.**
  **`grep OPENAI_API_KEY src/` must stay empty.** See [S2a] for the one
  neighbouring key that runtime code *does* read, and why it is a different
  variable.
- **[S2] ~~Journal semantic dedup uses pgvector on Neon, with embeddings from
  z.ai's `embedding-3`.~~ FALSIFIED BY MEASUREMENT — superseded by [S2a].**
  F15 was told to verify the endpoint before trusting the design, did so on
  2026-08-09, and found that **z.ai exposes no embeddings model of any kind**:
  `/models` lists only `glm-4.5`…`glm-5.2`, and every candidate model code
  (`embedding-3`, `embedding-2`, `embedding-4`, `embedding-v3`,
  `text-embedding-3`, `glm-embedding`) returns `400 code 1211 "Unknown Model"`
  on `/api/paas/v4`, on `/api/coding/paas/v4` and on `open.bigmodel.cn`.
  Independently, the key is a **coding subscription**: `/api/anthropic/v1/messages`
  answers 200 — which is the path the app actually uses, so nothing shipped is
  broken — while `/api/paas/v4/chat/completions` answers `429 code 1113
  "Insufficient balance"`. Recorded rather than deleted, because the next person
  to reach for z.ai embeddings should find the measurement instead of repeating
  it. F15's header block holds the full evidence table.
- **[S2a] Journal semantic dedup uses pgvector on Neon, with embeddings from
  OpenAI `text-embedding-3-small` (1536 dims).** The user's decision on
  2026-08-09, after [S2] was falsified. Two consequences that amend the rules
  above, both deliberate:
  - **Journal text leaves for a second data processor.** [S2] chose z.ai partly
    to avoid this. The journal is the most personal content in the app, and this
    was put to the user as the central cost of the option; they chose it anyway.
  - **[S1]'s "no application code may read it" is narrowed, not broken.** The
    embedding key is a **separate variable, `EMBEDDING_API_KEY`**, and should be
    a **separate OpenAI project key** scoped to embeddings — not the badge-art
    secret pasted twice. That keeps `grep OPENAI_API_KEY src/` empty as a
    testable property, and keeps the offline-tooling key and the runtime key
    independently revocable. F15 [D7] owns the mechanics.
  - **1536 is asserted, not measured.** No vector was obtained during planning.
    F15 §7.3 requires one curl to count the array *before* the `vector(N)`
    migration is generated — on an empty table that correction is one migration;
    after a backfill it is a re-embed of everything.
  - F15 ships in two phases. **Phase A needs no provider at all** and delivers
    the whole warn-and-override UX on normalised-hash matching; Phase B adds
    pgvector behind the same interface.
- **[S3] Sharing is opt-in and token-addressed.** A `shares` row with an opaque
  random slug is created only when the user taps Share. No entity uuid ever
  appears in a public URL, and revoking is deleting the row. Guessing a slug must
  be infeasible.
- **[S4] A journal near-duplicate warns; it does not block.** The user is shown
  the entry they already have and a way to save anyway. This is a deliberate
  softening of the user's word "forbid", agreed in conversation, because
  `src/app/api/journal/route.ts` documents the opposite decision at length —
  "the same saying may be met twice and kept twice, and a rejection at the exact
  moment the screen promises frictionless saving would be the worst possible
  trade". The warning respects both: it never loses a save, and it never lets a
  duplicate through unnoticed. **F15 must record this reversal in that route's
  comment rather than silently deleting it.**

## Reconciliation — where two plans contradict each other

The eight were written in parallel by agents that could not see each other. These
are the seams found by reading them side by side afterwards. **Where a plan
disagrees with a ruling here, this section wins**, and the losing plan's own text
should be corrected in the session that touches it rather than left to mislead
the next reader.

### [C1] The OAuth intent cookie is F17's `dw_claim`, not F16's `dw_share_intent`

F16 §5 froze a cookie named `dw_share_intent` holding a bare slug. F17 designed
`dw_claim`, holding `v1.<base64url(slug|tz|exp)>.<hmac-sha256 over AUTH_SECRET>`
with a 10-minute TTL. F18 built on F17's.

**F17's wins**, on the merits rather than on the head count: it is signed, so a
hand-forged cookie cannot aim the claim at an arbitrary share; it carries a TTL
inside the signed payload rather than trusting `Max-Age`; and it carries the
detected timezone, which F17 needs because **writes may not fall back to a
default timezone** and the claim performs a write.

Both agree on the two things that actually break the feature if got wrong —
`HttpOnly` and **`SameSite=Lax`, never `Strict`** (a `Strict` cookie is not sent
on the top-level navigation back from Google, which is precisely when it is
read). F16's `share:check` assertions on the cookie must be rewritten against
`dw_claim`'s shape, and `lib/share/intent.ts` becomes F17's signed reader.

### [C2] F17's claim payload must carry a word position, for F18

F18 shares a **card**, so the slug identifies six words. Its "practise this word"
needs to say *which*. F18 raises this as its R1 and proposes
`slug|w|tz|exp` with `getShareTargetForClaim(slug, w)`.

**Accepted.** `w` is an **index into the card, `1`–`6`, never a vocab uuid** —
which is the whole point, and consistent with [S3]'s ban on entity uuids in
public surfaces. It rides in the signed cookie rather than as a `?w=` query
param on `/claim`, because F17 deliberately froze that path to a literal with no
user data in it, and that is what structurally kills the open-redirect class.
`resolveClaimOutcome` and F17 §5's outcome table are untouched. **F17's session
should implement `w` from the start** — it is a smaller change than retrofitting
it, and F18 cannot ship without it.

### [C3] The badge art path lives in F12's generated `badge-art.ts`, not in F13's `badge-meta.ts`

Both plans gave the art path a home. F12 generates
`src/lib/gamification/badge-art.ts` as a total `Record<BadgeKey, BadgeArt>` —
regenerated by `make_badge_assets.py`, carrying content-hashed filenames, and
serving as a **compile-time parity guard**: a badge key with no art fails
`npm run typecheck`. F13 put an `art: string | null` field inside its hand-written
`badge-meta.ts`.

**F12's wins.** It is generated, so it cannot drift from the files on disk; the
filenames are content-hashed, so no human should be typing them; and the total
`Record` is a stronger guarantee than F13's `existsSync` assertion. Therefore:

- `BadgeMeta` drops `art`. It keeps `condition` and `gloss` — prose a human
  writes — and nothing a script owns.
- `BadgeMedal` reads `BADGE_ART[key]`, not `BADGE_META[key].art`.
- F13's "flip fourteen `art: null` values to paths" step (its §7 step 11) becomes
  "run `make_badge_assets.py`", which is less work and less error.
- F13 §4.4's asset requirements were written before F12's plan existed. **F12's
  decisions win on every point of detail** — 768×768 + 160×160 WebP, no
  transparency, a self-carried cream paper plate rather than an alpha channel.
  F13 already records this as its R7.
- Until F12 lands, `BADGE_ART` is absent and `BadgeMedal` renders F13's
  placeholder. F13 remains shippable on its own.

### [C4] F11 and F18 both touch `DailyCardRow`, and they compose

F11 makes the row pass an origin: `vocabDetailHref(item.id, 'today')`. F18 adds
an **optional `href` prop** defaulting to that same call, so a public shared card
can point its rows at `/s/<slug>/<1..6>` instead.

No conflict, but the order matters: **F11 first.** If F18 lands first, its
default `href` is written without the origin and F11's session has to find it
again in a second file. Whichever runs second should check that the default still
carries `'today'`.

## Facts about the codebase every plan needs

Verified by reading the code on 2026-08-09, not from the F1–F10 plans.

- **Model access is GLM via z.ai**, `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`,
  through `src/lib/llm/client.ts`. `@anthropic-ai/sdk` is a dependency but the
  client is OpenAI-compatible-shaped. One prompt module per feature under
  `src/lib/llm/prompts/`.
- **Auth is Auth.js v5 with Google as the only provider.** `src/app/signin` is
  the entry; `signInWithGoogle` is a server action in `src/lib/auth/actions`.
- **`src/app/(app)/layout.tsx` calls `requireOnboardedUser()`.** Every route in
  that group is gated on `profiles.onboarded_at`. `/onboarding` and `/signin` are
  siblings of the group, not members. **Public share routes must also be siblings
  — putting them inside `(app)` makes them require a session, which defeats the
  feature.** This is the single most likely mistake across F16–F18.
- **`vocabDetailHref` / `vocabChatHref` / `vocabListHref` live in
  `src/lib/vocab/links.ts`** and are imported by seven call sites across F4, F5,
  F6 and F8. That file is the correct place to add origin or share URLs; a
  template literal in an eighth file is how it drifts.
- **`POST /api/vocab` already handles the exact-duplicate case**: the insert
  races against `UNIQUE (user_id, lower(term))`, catches 23505, re-reads and
  returns `{ duplicate: true }` with the existing row. `add-word-form.tsx` and
  `enrichment-card.tsx` already render that state. F14 extends this; it does not
  invent it.
- **`suggestedCorrection` already exists** on `vocab_entries` and is written by
  enrichment ([R9]). The unhandled case F14 owns is: the correction the model
  returns is a term the user *already has*.
- **`lib/vocab/dedup.ts` and `lib/vocab/normalize.ts` are different functions
  that must not be merged.** `dedup` answers "are these the same word?" and
  destroys case, diacritics and punctuation; `normalize` answers "what did the
  user type?" and preserves all three. Under-folding is the correct failure mode.
- **`badges_awarded` has no metadata**: `badge_key`, `awarded_for_date`,
  `created_at`. Titles live in `BADGE_CATALOG` in `src/lib/gamification/badges.ts`
  and there is currently **no description text anywhere** — F13 is writing it for
  the first time. There are thirteen badges; `evaluateBadges` is **pure by
  contract** because `npm run stats:recompute` replays it, and a new rule must
  keep it pure.
- **`user_stats` is a cache and is never displayed** ([R11]). Every consumer
  recomputes from `daily_cards`.
- **Every "day" boundary goes through `src/lib/time/local-date.ts`**, the only
  file allowed to construct `Intl.DateTimeFormat` or do date arithmetic. `date`
  columns are `'YYYY-MM-DD'` strings. `grep toISOString` must not gain a hit
  outside `lib/cards/serialize.ts`, `lib/chat/serialize.ts` and
  `lib/journal/{serialize,cursor}.ts`.
- **All Drizzle access goes through `src/lib/db/queries/<resource>.ts`**, with
  `userId` as the first parameter of every function and in every WHERE clause.
  A public share query is the *one* exception in this batch and must be a named,
  commented departure — see F16.
- **Route handlers use `requireApiUser()` + `ok()` / `fail()`** from
  `src/lib/api/`. Envelope is `{ error: { code, message } }` and `message` is
  shown to the user verbatim.
- **Never import a zod schema as a value from a client component** — import the
  inferred type. One value import put 73 kB of zod into `/vocab/new`.
- **`import 'server-only'`** at the top of everything under `lib/db/`, `lib/llm/`
  and `lib/env.ts`.
- **Element-level CSS in `globals.css` must sit in `@layer base`**, or it beats
  every utility class silently.
- **Port 3200 is the only port.** Kill by pid, never by pattern.

## Conventions these plans must add to

- **Every new feature ships an offline check script** and a `package.json` entry,
  following `npm run journal:check` / `discover:check`: pure logic, no database,
  no network, runnable in CI. Features touching the database add a `:db` script
  that seeds a fixture and rolls back. Features whose *output is a prompt* add a
  `:dry-run` that makes real model calls and writes nothing — because in those
  features the prompt is the deliverable and an exit code only reports transport.
- **New migrations go through `npm run db:generate && npm run db:migrate`.**
  Never hand-edit `drizzle/`.
- Database columns `snake_case`, TypeScript `camelCase`. zod 4 spelling:
  `z.uuid()`, not `z.string().uuid()` ([R2]).

## What each plan must contain

Write to `plans/F<n>-<slug>.md`. Aim for something a fresh Claude session can
execute with no other context than the repository, `CLAUDE.md`, the roadmap and
this brief.

1. **Header** — one paragraph on what the feature is and the user's own words for
   why. Then a line naming which sections of which *other* plans it supersedes,
   if any.
2. **Decisions** — numbered, with rationale. Every place the plan departs from an
   existing documented decision must be called out, quoting the comment it
   overrides.
3. **Schema changes**, if any: the exact Drizzle snippet, the index rationale, and
   whether a migration is needed. Say explicitly when none is.
4. **Files** — a table of every file created or modified, one line each on why.
5. **Implementation order** — steps a session can follow top to bottom, each
   ending somewhere the app still builds.
6. **Verification** — the check scripts, what they assert, and the manual passes
   that no script can cover.
7. **Risks and open questions** — especially anything the plan could not verify
   without running it.

Be concrete. Name real files at real paths. Where you are guessing, say so in
the risks section rather than writing a confident sentence.
